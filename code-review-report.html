Executive Summary — Not production-ready

The application's entire security model is client-trusted. Every Convex function authenticates callers by accepting a walletAddress string as an argument, and the SIWE flow never verifies signatures server-side (convex/auth.ts:85: “we trust the frontend verification”). Any user can act as any wallet — including org admins — by simply passing that address to any API call. This defeats the RBAC system entirely and exposes fund movement, role management, and billing controls. For an app whose purpose is moving treasury funds, this must be fixed before anything else.

Beyond auth: payments are recorded as executed without on-chain verification, plan upgrades are trusted from client-supplied transaction data, the scheduled relay submits Safe transactions without checking signature thresholds, CSV exports are vulnerable to formula injection, and the whole backend test suite is broken (137 of 190 tests failing), so none of this is currently caught by CI.

Critical Findings

CriticalC-01Full authentication bypass — identity is whatever the caller claims
convex/auth.ts:85-87convex/lib/rbac.ts:10-49(pattern in every convex/*.ts module)

Every query and mutation takes walletAddress: v.string() from the client and uses it directly to look up users/memberships. There is no session token, no HTTP auth header, no signature check — the address is the only credential. The comment in the code acknowledges it:

// convex/auth.ts:85
// Note: In production, you would verify the signature here using viem
// For now, we trust the frontend verification
// The signature verification happens client-side with wagmi/viem

Impact: complete account takeover. A single curl can list another org's disbursements, create/execute payments, promote/demote members, link/unlink Safes, or upgrade billing — as any wallet. RBAC (requireOrgAccess) is correctly implemented but is built on an unauthenticated input, so it provides zero real protection.

  • Fix: verify the SIWE signature server-side with viem's verifyMessage (+ EIP-127/6492 for Smart Accounts) inside verifySignature.
  • Issue an opaque session token (random, hashed-at-rest) returned to the client and required via Authorization-style arg/header on every call; resolve identity from the token, never from a body parameter.
  • Convex supports this pattern well — consider Convex Auth or custom JWT auth so ctx.auth.getUserIdentity() replaces every args.walletAddress (~30+ call sites).
CriticalC-02Payments marked "executed" with fabricated tx hashes; no status state machine
convex/disbursements.ts:293-423

updateStatus accepts arbitrary transitions from any allowed role: draft → executed directly, or re-opening cancelled items. The client supplies txHash/safeTxHash and nothing validates them against the chain, the Safe Transaction Service, or even format. Combined with C-01, anyone can record phantom executed payments for audit/compliance purposes.

  • Fix: enforce a transition map (e.g., draft→pending→proposed→relaying→executed) server-side; only internal actions/scheduled jobs may set terminal states after verifying on-chain receipt via RPC or Safe API.
  • Add checksum validation on hash inputs and cross-check txHash against the expected Safe tx before marking executed.
CriticalC-03Billing upgrades trust client-declared payment
convex/billing.ts:106-162

subscribe / upgradeToPro accept txHash and paidThroughAt from the client and activate the plan immediately. No payment is verified on-chain — amount, recipient, token, and recency are unchecked. Any admin (or anyone, given C-01) gets Pro forever with a random hex string and an epoch far in the future.

await ctx.db.patch(billing._id, {
  plan: args.plan,
  status: "active",
  paidThroughAt: args.paidThroughAt, // client-controlled!
  ...
});
  • Fix: verify the payment server-side: look up txHash via RPC/Safe API, confirm transfer of correct amount/token to the Disburse treasury address, derive paidThroughAt from the verified payment — never accept it as input.
CriticalC-04Scheduled relay executes Safe transactions without threshold/signature validation
convex/relay.ts:230-330

fireScheduledRelay fetches the Safe tx from the transaction service, packs whatever confirmations exist into a signatures blob, and POSTs it to Gelato's public call-with-sync-fee endpoint — without checking confirmations.length ≥ confirmationsRequired, without verifying signature validity, and without an API key or sponsorship setup.

  • If under threshold: execTransaction reverts on-chain but the sync fee is still consumed → silent loss of gas funds from the Safe.
  • No re-validation that the safeTx payload still matches what was approved/approved by the disbursement record.
  • Gelato relays require payment configuration (1Balance or fee transfer); unauthenticated calls will fail in production or drain whoever sponsors them.
  • Fix: assert threshold met before encoding; use the Safe SDK server-side (@safe-global/protocol-kit) which handles signature ordering/validation; configure Gelato sponsorship properly and store credentials in env (server-side, non-VITE).
CriticalC-05Entire backend test suite broken — 137 tests fail before running assertions
vitest.config.ts:17-37node_modules/convex-test/dist/index.js:1053

All 11 Convex test files fail with TypeError: (intermediate value).glob is not a function thrown from convexTest(). This is a known incompatibility between convex-test and Vitest 4's module runner (the repo pins vitest ^4.0.17). Only 2 frontend test files pass. The suite that would have caught C-01/C-02/C-03 gaps cannot run at all.

  • Fix: pin vitest to ^3.x (or upgrade convex-test when it gains Vitest 4 support), then wire bun run test:run && bun run lint && tsc -b into CI so regressions are impossible to merge silently.
CriticalC-06Invite flow grants immediate active access with no acceptance step
convex/orgs.ts:404-534

inviteMember creates the membership row with status: "active" instantly — there is no invitation token, email/notification, or acceptance flow. Any admin can add any wallet address as an active member of any role, including admin. With C-01, membership equals access.

  • Fix: create memberships as invited; require the invited wallet to sign a claim message (post-auth-fix) to flip to active; cap assignable roles and notify existing admins.

High Severity

HighH-01CSV export vulnerable to formula injection
src/lib/csv.ts:61-74

escapeValue quotes commas/newlines but does not neutralize leading = + - @ \t. Beneficiary names, memos, and notes are attacker-influenceable (bulk CSV import, free-text fields) and are exported to Reports CSVs. Opening in Excel/Sheets can execute formulas (e.g., =WEBSERVICE(...)) or exfiltrate via DDE — a classic issue in finance tooling.

  • Fix: prefix dangerous leading characters with ' (apostrophe) or a tab, per OWASP CSV injection guidance.
HighH-02Monetary amounts parsed as floats; no decimal/limit validation
convex/disbursements.ts:649-654convex/disbursements.ts:172-177

Amounts are stored as strings (good) but validated with parseFloat and summed with float arithmetic for batch totals: totalAmount += amountNum. Precision drift, scientific notation ("1e21"), and garbage like 12abc.5 slip past. No per-token decimal checks or max-amount caps exist; sorting also compares via parseFloat.

  • Fix: validate with regex ^\d+(\.\d{1,decimals})?$ against token decimals, sum in integer base-units with BigInt, and enforce sanity caps.
HighH-03Wallet-address inputs barely validated
src/lib/csv.ts:290-291convex/auth.tsconvex/beneficiaries.ts

Validation reduces to startsWith('0x') && length === 42 — non-hex characters pass. Backend functions lowercase whatever arrives with no checksum/format gate. Invalid addresses propagate into beneficiaries, deposits denormalization, and eventually on-chain transfer calldata (where they revert late, wasting gas and approval time).

  • Fix: validate with viem isAddress() at both boundaries; reject (or normalize-and-record) mixed-case strings that fail EIP-55 checksums on import.
HighH-04Unauthenticated queries leak org data
convex/orgs.ts:186-191convex/billing.ts:211-235

orgs.get and billing.isActive take only an org ID with no access check — org name, creator, screening-enforcement mode, and subscription state are enumerable by ID guessing. Inconsistent with the rest of the codebase where checks exist (even if undermined by C-01).

HighH-05Unsafe signature ordering in hand-rolled execTransaction encoder
convex/relay.ts:68-100

Safe requires signatures sorted ascending by signer address. The encoder sorts checksummed addresses with localeCompare, whose collation is locale-dependent and case-aware — not guaranteed to equal byte-order comparison of lowercase hex. Misordered signatures produce invalid execTransaction calldata (revert + lost relay fee). Hand-building this ABI payload also bypasses protocol-kit's contract-signature handling.

  • Fix: sort by owner.toLowerCase() plain comparison, or better: build the transaction with protocol-kit server-side instead of manual ABI encoding.
HighH-06Session lifecycle weaknesses
convex/auth.ts:33-49, 75-91, 145-161

Sessions are keyed solely by wallet: generating a nonce deletes all other sessions for that wallet (logout-by-login across devices), the nonce is checked via substring message.includes(nonce), is never deleted/consumed after use (replay within window), and expired sessions are lazily cleaned only on access. No binding to issuer/domain in the SIWE message is enforced server-side (nothing is enforced server-side).

  • Fix: consume nonces on use, parse and validate full SIWE message fields (domain, uri, issuedAt, expirationTime), rotate tokens, and index expiry for a periodic cleanup job.

Medium Severity

MediumM-01disbursements.list loads entire org history + N+1 enrichment per request
convex/disbursements.ts:42-120

list collects every disbursement for the org, then for each batch runs one query per recipient plus one db.get per beneficiary — then filters/sorts/paginates in memory. Cursor pagination is fake (index over the full array). At thousands of rows this blows past read limits and latency budgets on every page view.

  • Fix: push filters into indexed queries (by_org_status exists), paginate with real cursors, and denormalize a searchable display-name onto the disbursement row at write time.
MediumM-02Deposit sync: unbounded pagination loop, per-row mutations, same-second skips
convex/deposits.ts:97-179

The while (nextUrl) loop has no page cap; each insert is its own runMutation (slow, expensive); the incremental cutoff uses eventTimestamp <= sinceTimestamp, which permanently skips transfers sharing the latest recorded timestamp.

MediumM-03User creation race condition — duplicate wallets possible
convex/auth.ts:14-26convex/orgs.ts:458-470

Both generateNonce and inviteMember do check-then-insert on users.walletAddress. Convex doesn't enforce unique indexes; two concurrent calls create duplicate users, splitting memberships/history across identities.

  • Fix: serialize inserts through a deterministic-ID pattern (derive _id from the wallet) or retry-on-conflict logic.
MediumM-04God components — five pages exceed ~1,200 lines
src/pages/Disbursements.tsx (2,720 lines)Reports.tsx (1,347)Beneficiaries.tsx (1,286)Dashboard.tsx (1,265)Settings.tsx (1,200)

These files mix data fetching, business rules, modals, charts, and inline form logic. This drives slow onboarding, merge conflicts, and the seven react-hooks/exhaustive-deps warnings currently emitted in Dashboard (stale-memo risk around currency formatting functions defined during render).

  • Fix: extract feature folders (hooks for queries, presentational components, modal children); move formatters to module scope to fix the lint warnings.
MediumM-05Screening enforcement has bypass paths and weak matching surface
convex/disbursements.ts:331-366convex/screening.ts:43

OFAC blocking runs only when status moves to pending/proposed through updateStatus — but batch creation, direct schedule, and (per C-02) arbitrary transitions don't consistently funnel through it; results are fetched with unindexed .filter. Fuzzy matching at 0.85 Levenshtein similarity is reasonable but aliases/transliterations coverage depends entirely on the import script's data quality, and there's no re-screening when the SDN list updates.

MediumM-06auditLog metadata typed v.any(); audit trail not append-only by design
convex/schema.ts:242-252

Compliance-critical log allows arbitrary shapes and rows are mutable documents — any writer can patch/delete history (and with C-01, anyone can). For a product selling compliance features, log writes should be validated, append-only, and possibly exported periodically.

MediumM-07Server code reads VITE_-prefixed env vars
convex/orgs.ts:9,19-21,27-41

Convex functions read process.env.VITE_GELATO_DEFAULT_FEE_TOKEN, VITE_DISBURSE_BENEFICIARY_*, etc. The VITE_ prefix convention means "bundled into client output" — using it for server-side defaults is confusing and risks someone later putting a genuinely sensitive value behind the prefix expecting it to stay private. Also duplicated config between .env and .env.local.

MediumM-08Repo hygiene: 105MB OFAC XML adjacent to repo, dead mockups file, dist/ artifacts
sdn_enhanced.xml (105MB, gitignored but local)treasury-mockups.jsx (untracked)dist/

The SDN dataset and design mockups live in the repo root untracked; dist/ build output persists locally. None are committed (verified), but they invite accidental staging. Consider a data/ dir documented in README and a stricter root layout.
